Computer Architecture

Selected digital design and architecture projects emphasizing clean structural HDL, datapath-level thinking, and a verification-first workflow. I focus on making complex systems legible: clear module boundaries, explicit control signals, and testbenches that tell you what failed and why.

Highlighted Projects

32-bit ALU (SystemVerilog)

Built a structural 32-bit ALU supporting arithmetic, logic, comparison, and shifts with flag generation and opcode-controlled output selection. The goal was reliability and readability: predictable datapath behavior and clear verification of edge cases.

Tools / Topics: SystemVerilog · Datapath design · Carry-lookahead structure · Mux trees · Flags · Testbench

How I worked

  • Designed for clarity: separated sub-blocks (adder, logic unit, shifter) and combined outputs with explicit selection.
  • Made behavior explicit: documented opcode → function mapping and flag semantics so review was fast.
  • Verified edge cases: tested overflow, shift boundaries, and comparisons with representative vectors.
  • Communicated in a checklist: “spec → implementation → tests → results,” so someone else could validate quickly.

Implementation snapshot

  • Carry-lookahead style structure for predictable addition behavior with clean internal naming.
  • Unified result selection with an opcode-driven mux structure.
  • Flags generated from final output + arithmetic status signals.

What I’d optimize next

  • Add randomized stimulus and functional coverage for stronger confidence.
  • Introduce lightweight assertions for invariants (e.g., Zero flag correctness).

Multicycle CPU (SystemVerilog)

Built a multicycle CPU using a clean datapath + controller split. I followed a control-first workflow: map instruction classes to a state machine, implement the baseline execute/writeback loop, then extend support to immediates, memory operations, and control flow—without breaking the core architecture.

Tools / Topics: SystemVerilog · CPU architecture · FSM controller · ISA reasoning · Branch/jump control · Verification programs

What it supports

  • R-type: add, sub, and, or, xor, nor, sll, srl, sra, slt
  • I-type: addi, andi, ori, xori, slti
  • Memory: lw / sw
  • Control flow: beq, bne, j, jal, jr (+ nop)

How I worked

  • Control-first planning: wrote instruction paths and control signals per state before coding.
  • Kept boundaries strict: datapath owns state; controller drives only control signals.
  • Built incrementally: shipped R-type first, then expanded ISA support without reworking the architecture.
  • Debugged transparently: used internal observability (PC/IR/ALUOut/state) to isolate failures to control vs datapath.

Implementation snapshot

  • Controller FSM selects state path via opcode/funct (explicit paths for JR/JAL/branch/mem).
  • PC source mux supports PC+4, branch target, jump target, and JR (rs).
  • Immediate handling uses sign/zero extension based on instruction class.
  • Branch targets computed early; PC enable uses branch signal + ALU Zero for beq/bne.

Verification approach

  • R-type program: validated ALU ops and shifts.
  • Mixed program: immediates + lw/sw + beq/bne + j/jal/jr to hit control edges.
  • Debug discipline: tracked “expected vs observed” at state boundaries to catch off-by-one control bugs.

What I’d optimize next

  • Add assertions for safety rules (e.g., RegWrite only in WB states; MemWrite only in SW state).
  • Increase coverage for corner cases (branch taken/not-taken, JR behavior, memory assumptions).

Traffic Light Controller (Moore FSM, One-hot)

Implemented a one-hot Moore FSM traffic light controller driven by a 1 Hz tick and an external 5-bit down-counter. The design enforces minimum green, supports a cuttable extension window based on opposing demand, and includes safe interlock all-red phases. Emphasis: deterministic timing and readable control logic.

Tools / Topics: SystemVerilog · One-hot Moore FSM · Timer handshake · Deterministic timing · Instrumented testbench

How I worked

  • Defined invariants upfront: minimum green holds, interlock all-red occurs, outputs default safe.
  • Designed handshake cleanly: timer loads only on state entry, durations mapped from state intent.
  • Kept logic reviewable: one-hot encoding for easy inspection and fast debugging.
  • Verified with instrumentation: logged loads and transitions to confirm timing + early-cut behavior.

Implementation snapshot

  • Durations encoded as a small mapping (state → seconds), loaded on entry.
  • Extension window ends early when opposing demand is present (or timer expires).
  • Moore decode defaults to all-red / don’t-walk, overridden per active state.

What I’d optimize next

  • Add self-checking assertions for timing and safety invariants.
  • Expand scenario set (bursty demand, alternating demand) and measure fairness properties.
